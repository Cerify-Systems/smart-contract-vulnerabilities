# Fix

## Root Cause

The protocol used a current PancakeSwap reserve as a trusted price input for an operation that could mint a valuable token.

This is unsafe because an attacker can temporarily move AMM reserves with flash-loaned capital.

## Required Mitigation

### 1. Replace spot reserves with a manipulation-resistant oracle

Do not rely solely on:

```solidity
pair.getReserves()
```

for reward-critical valuation.

Possible alternatives include:

- TWAP pricing;
- independent oracle feeds;
- multiple price sources;
- delayed pricing;
- bounded price movement.

### 2. Cap minting

Even with an oracle, reward minting should have hard limits.

Useful protections include:

```text
maximum reward per transaction
maximum reward per block
maximum reward relative to actual fees
```

### 3. Separate fee accounting from spot price

The amount of BUNNY minted should be based on the actual fee/profit generated by the vault rather than on a same-transaction manipulable LP valuation.

### 4. Test flash-loan manipulation

A security test should:

1. create a large temporary AMM imbalance;
2. call the vault reward function;
3. execute the minter path;
4. verify that reward issuance remains bounded.

### 5. Review external protocol assumptions

PancakeBunny composed PancakeSwap LPs, routers and price calculations. External AMM state should be treated as adversarial input.

## Security Principle

The unsafe architecture was:

```text
AMM spot reserve
      ↓
LP price
      ↓
reward calculation
      ↓
BUNNY mint
```

A safer architecture is:

```text
manipulation-resistant oracle
      ↓
bounded LP valuation
      ↓
verified fee amount
      ↓
bounded BUNNY mint
```
